# DevOps Assessment - Terraform + Database Reliability

Terraform code for an AWS setup (Internet -> ALB -> ECS/Fargate -> RDS) plus a
local PostgreSQL environment for the database tasks: migrations, seed data,
query optimisation, backup and restore.

Stack: Terraform, AWS, Docker Compose, PostgreSQL, GitHub Actions, shell scripting.

As stated in the assignment, there is no actual AWS deployment here. The
Terraform side is checked with `fmt`, `init`, `validate` and `plan`. The
database side runs locally on Docker Compose.

## Requirements

- Terraform 1.6 or newer (I used 1.15.8)
- Docker with Compose v2

No PostgreSQL client is needed on the host. The scripts run `psql`, `pg_dump`
and `pg_restore` inside the container.

## Layout

```
infra/
  modules/
    network/        VPC, subnets, NAT, route tables, security groups
    ecs/            ALB, target group, listener, cluster, task definition, service
    rds/            subnet group, parameter group, instance, Secrets Manager
  envs/
    dev/            variables.tf, terraform.tfvars, backend.tf, backend.hcl
    prod/           same files, different values
  bootstrap/        S3 buckets for remote state (run once per account)

db/
  migrations/       0001 bookings table, 0002 events table, 0003 indexes
  seed/             0100_seed.sql
  queries/          target query, EXPLAIN, index list, data profile

scripts/
  backup.sh         timestamped dump
  restore.sh        restore into a fresh database and check it
  explain.sh        query plan with and without the index
  lib/common.sh     shared helpers

.github/workflows/
  terraform.yml     fmt, init, validate, plan on pull requests
```

## Part 1 - Terraform infrastructure

```
Internet -> ALB (public subnets) -> ECS Fargate (private subnets) -> RDS (private subnets)
```

Included: VPC with public and private subnets across multiple AZs, NAT gateway
for outbound traffic from the private subnets, security groups for the ALB, the
ECS tasks and RDS, an ECS cluster with a task definition and service, and an RDS
PostgreSQL instance. The container image is nginx, since the assignment allows a
placeholder.

RDS is private and only reachable from the ECS tasks:

- `publicly_accessible = false`
- the DB subnet group only contains private subnets, which have no route to the
  internet gateway
- the RDS security group has a single ingress rule, and it references the ECS
  task security group rather than a CIDR block. There is no IP address you can
  add anywhere to get in
- the RDS security group has no egress rules

The ECS tasks run with `assign_public_ip = false`, so they are only reachable
through the ALB.

The three security groups are defined in the network module rather than in the
ecs and rds modules. They reference each other, and the ecs module also needs an
output from the rds module (the credentials secret ARN). If ecs owned the group
that rds depends on, the modules would form a cycle and Terraform would not
build it.

The RDS master password is generated by Terraform and stored in Secrets Manager.
The ECS execution role can read that one secret, and the ECS agent passes it to
the container at startup. It is not in any tfvars file.

### Running it

```bash
cd infra/envs/dev        # or infra/envs/prod
terraform fmt -check -recursive ../..
terraform init
terraform validate
terraform plan -refresh=false
```

These work without an AWS account or credentials. The `plan_only` variable
defaults to `true`, which skips the AWS provider's credential check - without it
the provider calls `sts:GetCallerIdentity` while configuring itself and the plan
fails before it looks at any resource. For a real deployment, turn it off:

```bash
terraform apply -var plan_only=false
```

`terraform plan` gives 47 resources for dev and 62 for prod.

## Part 2 - Environments

Both environments call the same modules. Everything that differs is a value in
`terraform.tfvars`.

| | dev | prod |
| --- | --- | --- |
| VPC CIDR | 10.20.0.0/16 | 10.30.0.0/16 |
| Availability zones | 2 | 3 |
| NAT gateways | 1 shared | one per AZ |
| ECS task size | 256 CPU / 512 MB | 1024 CPU / 2048 MB |
| ECS task count | 1 | 3 |
| ECS Exec | enabled | disabled |
| ALB deletion protection | false | true |
| Log retention | 7 days | 90 days |
| RDS instance class | db.t4g.micro | db.m6g.large |
| RDS Multi-AZ | false | true |
| RDS backup retention | 1 day | 30 days |
| RDS deletion protection | false | true |
| Final snapshot on destroy | skipped | taken |
| Performance Insights | off | on |
| Changes applied | immediately | in maintenance window |

Each environment has its own `backend.hcl` with a separate S3 bucket and state
key, so a dev credential cannot touch prod state:

```hcl
bucket       = "hotelbook-tfstate-prod-ap-south-1"
key          = "envs/prod/terraform.tfstate"
region       = "ap-south-1"
encrypt      = true
use_lockfile = true
```

The `backend "s3"` block in `backend.tf` is commented out so that a plain
`terraform init` works with no bucket and no credentials. To use remote state,
create the buckets with `infra/bootstrap`, uncomment the block, then:

```bash
terraform init -backend-config=backend.hcl
```

## Part 3 - GitHub Actions

`.github/workflows/terraform.yml` runs on pull requests that touch `infra/`:
`fmt -check`, then `init` and `validate` for each module, then `init`,
`validate` and `plan` for dev and prod.

The plan is shared three ways: as a pull request comment (one per environment,
updated in place instead of adding a new comment each push), as a workflow
artifact containing `plan.txt` and the binary plan file, and in the workflow
step summary.

## Part 4 - Local database

```bash
cp .env.example .env
docker compose up -d
docker compose logs db | tail -20
```

PostgreSQL 16. I picked PostgreSQL over MySQL because the schema in the
assignment uses `JSONB` and `BIGSERIAL`.

On the first start the official image runs everything in
`/docker-entrypoint-initdb.d` in filename order, so the numbered prefixes
control the order: `0001` and `0002` create the tables, `0003` creates the
indexes, `0100` loads the seed data. Each file is mounted individually because
the image only runs files at the top level of that directory and ignores
subdirectories.

To start over:

```bash
docker compose down -v && docker compose up -d
```

Two changes from the schema in the assignment:

- `created_at` is `TIMESTAMPTZ` instead of `TIMESTAMP`. The query in Part 5
  filters on `NOW() - INTERVAL '30 days'`, and comparing a naive timestamp
  against `NOW()` depends on the session timezone, which is a problem in IST.
  The container also sets `TZ=UTC`.
- `booking_events.booking_id` has a foreign key to `hotel_bookings(id)` with
  `ON DELETE CASCADE`. Without it the events table collects rows pointing at
  bookings that no longer exist.

I also added check constraints for `checkout_date > checkin_date`,
`amount >= 0` and the status values.

## Part 5 - Seed data and indexing

`db/seed/0100_seed.sql` inserts 800 bookings across 5 organisations, 8 cities
and 5 statuses, with events for about half of them and a cancellation or refund
event for the ones that did not complete.

The values come from `generate_series` and arithmetic rather than `random()`, so
the data is the same every time. That keeps the query plan reproducible and lets
`restore.sh` compare row counts between the source and the restored database.

Delhi is about 30% of the rows and `created_at` spans the last 73 days, so
roughly 40% of the rows fall inside the 30 day window. If every row were recent
the range condition would not filter anything and any index would look good.

```bash
docker compose exec -T db psql -U hotels_admin -d hotels -f /queries/04_data_profile.sql
```

### The index

```sql
CREATE INDEX idx_hotel_bookings_city_created_at
    ON hotel_bookings (city, created_at DESC)
    INCLUDE (org_id, status, amount);
```

`city` comes first because it is an equality condition, and `created_at` second
because it is a range. A B-tree can only use one range column, and only after
the equality columns. In this order the scan goes straight to `city = 'delhi'`
and then reads one continuous run of entries for the last 30 days. The other way
round, `(created_at, city)`, it would have to read every city's rows in the time
window and throw most of them away.

`org_id`, `status` and `amount` are only needed for the output, not for finding
rows, so they go in `INCLUDE`. That makes the index covering and the query is
answered by an index-only scan with no heap access. Keeping them out of the key
keeps the key small.

`DESC` is not needed for a `>=` condition, since a B-tree can be read in either
direction. It matches how the rest of the data is usually read (newest first),
so an `ORDER BY created_at DESC LIMIT n` on the same prefix also avoids a sort.

Other options I considered:

- separate indexes on `(city)` and `(created_at)`: the planner would combine
  them with a BitmapAnd and then read the table for each matching row to get
  `org_id`, `status` and `amount`. More I/O, and no index-only scan.
- `org_id` and `status` as key columns instead of `INCLUDE`: they would sit
  after a range column, so the index still cannot return rows sorted by
  `(org_id, status)`. The GROUP BY would need a hash step anyway and the key
  would just be wider.
- a partial index with `WHERE city = 'delhi'`: smaller, but it only serves one
  city and would need a new index every time a city is added.
- BRIN on `created_at`: good for a very large append-only table, but it does
  not help with the city lookup.

There are two more indexes: `(org_id, created_at DESC)` for per-organisation
queries, and `(booking_id, created_at DESC)` on `booking_events`. PostgreSQL
does not index the referencing side of a foreign key automatically, so without
the second one every delete on `hotel_bookings` has to scan the whole events
table for the cascade.

### Checking the plan

```bash
./scripts/explain.sh
```

This drops the index, runs EXPLAIN, recreates the index, runs `VACUUM (ANALYZE)`
and runs EXPLAIN again. It puts the index back even if interrupted.

Before:

```
HashAggregate  (cost=28.99..29.30 rows=25 width=65)
  ->  Seq Scan on hotel_bookings  (cost=0.00..28.00 rows=99 width=31)
        Filter: (((city)::text = 'delhi'::text) AND (created_at >= (now() - '30 days'::interval)))
        Rows Removed by Filter: 701
        Buffers: shared hit=12
```

After:

```
HashAggregate  (cost=11.25..11.56 rows=25 width=65)
  ->  Index Only Scan using idx_hotel_bookings_city_created_at on hotel_bookings  (cost=0.28..10.26 rows=99 width=31)
        Index Cond: ((city = 'delhi'::text) AND (created_at >= (now() - '30 days'::interval)))
        Heap Fetches: 0
        Buffers: shared hit=1 read=3
```

`Heap Fetches: 0` is the part that shows the index is covering. Rows thrown away
by the filter go from 701 to 0, buffers from 12 to 4, and estimated cost from
28.99 to 11.25.

Execution time is not useful at this size. The table is 12 pages and already in
memory, so both plans finish in well under a millisecond and the difference
between runs is noise. The numbers that matter are the ones above, because
`Rows Removed by Filter` grows with every row inserted while the index-only scan
keeps reading about the 99 rows that match.

`VACUUM` and not just `ANALYZE` matters here. An index-only scan still has to
check the table for pages the visibility map does not mark all-visible, so
without it the plan reports heap fetches above zero. The seed file does the same
thing at the end for the same reason.

## Part 6 - Backup and restore

```bash
./scripts/backup.sh
./scripts/restore.sh --force
```

Both accept `--help`.

`backup.sh` writes a timestamped dump to `backups/`, for example
`hotels_20261119_063540.dump`. It uses the custom format by default, which is
compressed and is what `pg_restore` needs for a selective restore;
`--format plain` writes a readable `.sql` file instead. It writes to a `.partial`
file first and renames it only on success, so an interrupted run does not leave
a half-written dump that looks usable. After writing it reads the archive's
table of contents back with `pg_restore --list` to confirm it is not corrupt,
stores a `sha256` next to it, updates a `latest.dump` symlink, and deletes dumps
beyond the most recent 10.

```bash
./scripts/backup.sh --label pre-migration
./scripts/backup.sh --keep 3
```

### How to verify the restore worked

`restore.sh` restores into a new database (`hotels` -> `hotels_restored`) rather
than over the original. The assignment asks for a fresh database, and it is also
the only way to show the dump is complete on its own: if you restore over an
existing database you cannot tell which rows came from the dump. Restoring over
the source needs `--into-source --force`.

Before restoring it checks the `sha256` against the value recorded at backup
time and refuses to continue if they differ, and reads the archive's table of
contents. After restoring it runs `ANALYZE` and compares the two databases:

```
  check                              source       restored result
  -------------------------- -------------- -------------- ------
  hotel_bookings rows                   800            800 match
  booking_events rows                  1113           1113 match
  SUM(amount)                   20422800.00    20422800.00 match
  indexes in public                       6              6 match

  ok referential integrity: no orphan booking_events
  ok covering index idx_hotel_bookings_city_created_at is present
```

It then runs the Part 5 query against the restored database and prints the
result. The script exits non-zero if anything does not match.

The checks are there for specific failures: row counts catch a partial restore,
`SUM(amount)` catches rows that restored with wrong values (a count alone would
not), the index check catches a restore that brings back data but loses indexes,
and the orphan check catches broken foreign keys.

To look at it yourself:

```bash
docker compose exec db psql -U hotels_admin -d hotels_restored -c 'SELECT COUNT(*) FROM hotel_bookings;'
```
